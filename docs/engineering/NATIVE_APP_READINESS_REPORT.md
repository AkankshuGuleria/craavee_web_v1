### The one override, and why

Pinning declared ranges was not enough. `next`, `motion`, `@phosphor-icons/react`
and `@expo/metro-runtime` all declare `react ^19`, so npm resolved the newest
match and reinstalled **19.2.8 at the root as an auto-installed peer** — npm
itself flagged it `invalid` against all three workspaces. `overrides` therefore
pins `react` and `react-dom` to `19.2.3`. It is limited to exactly the two
packages that must be singletons in a native build.

`package-lock.json` was regenerated by npm — not hand-edited. The stale lock
retained the old resolution and neither `npm install` nor `npm dedupe` would
collapse it. That regeneration is the large diff.

## 2. Metro configuration

`apps/customer-runner/metro.config.js` called `getDefaultConfig(__dirname)`
and set neither `watchFolders` nor `resolver.nodeModulesPaths`, so Metro
resolved only from this app's own tree. npm hoists `expo` and `react-native`
to the workspace root, and the NativeWind Babel preset sets `jsxImportSource`,
so `react-native-css-interop/jsx-runtime` was injected into hoisted files that
could not resolve it:

```
UnableToResolveError: react-native-css-interop/jsx-runtime
  from <root>/node_modules/expo/src/launch/withDevTools.ios.tsx
```

Both paths derive from `__dirname`, so the configuration is portable to CI and
EAS. No duplicated `node_modules`, no copied packages, no hardcoded paths, no
symlinks, no disabled resolution checks. **VERIFIED.**

A `resolver.blockList` for AppleDouble sidecars was also required — see §6.

## 6. exFAT AppleDouble sidecars break native builds at four layers

The repository lives on an exFAT volume, which cannot store macOS resource
forks inline, so the OS writes a binary `._name` companion beside every file it
touches. They are gitignored and harmless to git. They are **not** harmless to
any tool that globs for files:

| Layer | Failure |
| --- | --- |
| **Metro** | `TransformError: app/(auth)/._verify.tsx — SyntaxError: Unexpected character` |
| **CocoaPods** | `Invalid podspec file at .../ios/._ExpoDomWebView.podspec` |
| **CocoaPods** | `Could not automatically select an Xcode project` — `._Craavee.xcodeproj` shadows the real one |
| **Expo build scripts** | `find -delete` racing sidecars, then `sed: RE error: illegal byte sequence` |
| **Gradle** | `IllegalArgumentException (no error message)` — ASM parsing `._*` inside `build/classes/kotlin/main` |

Metro is fixed permanently via `resolver.blockList`. The `sed` failure is fixed
by `LC_ALL=C`. For the rest, `scripts/clean-apple-sidecars.sh` removes them.

**Cleaning does not solve it.** The files are recreated *while the build runs*,
as Xcode and Gradle write to the volume. Measured directly: after cleaning to
zero and starting a Gradle build, **228 sidecars had reappeared** under
`node_modules/@react-native/gradle-plugin` by the time it failed. The race
cannot be won at this location.

## 7. A regression I introduced, found and fixed

Declaring `react-native-css-interop` directly changed which `tailwindcss` npm
hoists. The workspace legitimately needs two majors — v4 for the Next.js apps,
v3 for nativewind — and v4 previously won the root **by accident**. With
css-interop direct, v3 hoists instead, and `packages/ui`, which declared no
tailwindcss at all, then resolved v3:

```
CssSyntaxError: Can't resolve 'tailwindcss' in packages/ui/src/styles
```

The Console build failed. Fixed by making `packages/ui` declare
`tailwindcss ^4.3.3` itself rather than depending on hoisting order — correct
regardless of which major wins, so the same break cannot recur when the graph
shifts again. **VERIFIED: both Next.js apps build.**

## 8. Native run commands

### iOS — **BLOCKED**, upstream defect

`npx expo run:ios` gets through prebuild, `pod install`, and compiles React
Native and every Expo module with **zero compile errors**. It then fails on one
CocoaPods script phase:

```
❌ Script '[CP-User] Generate app.config for prebuilt Constants.manifest' failed
```

The generated phase is:

```sh
bash -l -c "$PODS_TARGET_SRCROOT/../scripts/get-app-config-ios.sh"
```

`bash -c` re-splits the string it receives, so a path containing a space
becomes two words. Demonstrated directly:

```
bash -l -c "$VAR"        →  bash: /tmp/spaced: No such file or directory
bash -l -c "\"$VAR\""    →  script ran OK
```

The repository is at `/Volumes/T7 Shield/…`. This is an **upstream
`expo-constants` defect**, not a Craavee misconfiguration, and it is not
fixable from `metro.config.js`, `app.json`, or dependencies — the file is
regenerated into the gitignored `ios/` directory on every prebuild.

CocoaPods 1.17.0 was installed automatically by Expo, via Homebrew with its
**own** Ruby 4.0.6. The system Ruby was not touched.

This is not the first time this path's space has broken a toolchain:
`scripts/run-db-tests.sh` already documents `pg_prove` choking on it.

### Android — **BLOCKED**, sidecar race

`npx expo run:android` reaches Gradle 9.3.1 running on JDK 17.0.20.1 (the
correct JDK — confirmed via `gradlew --version`) and fails in
`InstrumentationAnalysisTransform` / `BuildToolsApiClasspathEntrySnapshotTransform`
with `java.lang.IllegalArgumentException (no error message)` — ASM refusing the
`._*` files described in §6. Cleaning first does not help, because the build
recreates them.

**NOT VERIFIED:** app installed, root screen rendered, navigation, reload — on
either platform. Reported as blocked rather than skipped.

## 13. What would actually unblock native builds

Both remaining blockers come from the repository's location, and neither is
fixable in this codebase:

1. **The space** in `/Volumes/T7 Shield/` breaks `expo-constants`' script phase.
2. **exFAT** regenerates AppleDouble sidecars mid-build, breaking Gradle and
   CocoaPods.

The single change that resolves both is **moving the repository (or at least
`apps/customer-runner` plus its `node_modules`) to a space-free path on the
internal APFS volume**. That is a decision for the machine owner and was
explicitly out of scope here; nothing was moved.

Until then: **Metro bundling works on all three platforms**, so JavaScript-level
work is fully verifiable locally, and EAS Build — which compiles on Linux/macOS
runners with neither constraint — remains the path to an installable artifact.
